# cp_0018 camera investigation — 2026-11-10

This is an investigation record, not a release approval. cp_0018 now runs the complete v8.2 candidate stack with code `b5f0c80776a29a2d8658ea401ce5d2d6cd59a349`; cp_0017/0020/0021/0022 have not been updated. Camera quality has not passed, so an active service is not an acceptance of this device.

## Subsequent full-stack test and Bluetooth maintenance

After installation of the complete candidate system stack, one preselected 121.441-second four-head-camera and IMU test completed START/ACK, refresh in the same session, web long-press STOP, native reap, shutdown, closed files and save. Four streams contained 3617–3627 frames and IMU contained 24205 rows. The existing QC marked five rear-left and one front-right 100 ms camd output-grid gaps as QC_ERROR. The session remains pending_qc; full long-video decode and host QC were not completed. These results do not establish a hardware root cause.

A single controlled BlueZ restart changed its PID and restored the agent registration and original enabled/active states. Systemd automatically killed the old agent after its configured stop timeout. Bluetooth configuration/trust hashes, camd PID and USB service PID remained unchanged. The first application scan submission returned HTTP 503 before discovery began while the sidecar was starting. After read-only checks confirmed the sidecar and proxy ready, the sole normal application scan was accepted with HTTP 202 but did not start discovery and finished as scan_busy. Earlier independent diagnosis captured BlueZ InProgress, but this does not establish its underlying cause. Bluetooth discovery, headset connection and audio remain unverified. No pairing or adapter reset was performed.

Read-only management READ_INFO showed hci1 supports BR/EDR but current settings `0x0a11` omit BR/EDR `0x80`; `/etc/bluetooth/main.conf` specifies `ControllerMode=le`, whereas the headset workflow requests BR/EDR discovery. A bounded attempt to enable BR/EDR online initially produced an unconfirmed result: its response parser incorrectly handled MGMT CMD_STATUS, and the original event was not retained. After the parser was corrected and tested offline, one recorded retry returned CMD_STATUS `0x0b` (Rejected); readback remained `0x0a11`, and the exact original configuration was restored. The matching upstream Linux 5.10 source rejects enabling BR/EDR while powered if secure connections are already enabled or a static address is configured; this device reports the secure-connections setting, but its Rockchip kernel is not proven identical. No further scan, security-setting change or restart was performed.

Subsequently, after confirmed idle and a restricted backup, hci1 was powered off, only the local `ControllerMode` was changed to `dual`, and BlueZ was reloaded once to initialize that mode. Readback `0x0a91` confirms powered, LE, BR/EDR and the original secure-connections bit; hci1 address, hci0 read-only state, camd and USB service PIDs were unchanged. Four other Bluetooth configuration/trust files matched their backups. The original bt-agent was automatically SIGKILLed by systemd after its existing stop timeout and the new agent registered. One normal application discovery actually started and ended without an error, with five candidates; no headset was paired or connected and audio was not tested. The original local configuration and restricted Bluetooth backup are stored on cp_0018, not in Git. This resolves the demonstrated mode mismatch for that limited discovery test, not the camera quality failure.

The device-specific consolidated candidate package and exact pre-candidate backup are at `/home/orangepi/TEST-headring-v81-20261109/headring-v8.2-final-cp0018`; 37 targets and two factory references verify. Rollback requires confirmed idle and matching device/state. The original v8.1 package is retained.

## Current evidence

- The rear-left (`bleft`) channel intermittently reports `snapshot_ready` through camd STATUS while an actual NV12 snapshot and H.264 read both time out. With the controller and preview consumers stopped, the same failure persisted. A single controlled camd restart temporarily restored fresh snapshots and H.264, but the problem later recurred. Status alone is therefore not evidence of current frames. The candidate's scan reports this as an error while retaining the other three successful channels.
- The front-right (`right`) recording had repeated 100 ms gaps in **camd output's CLOCK_REALTIME frame grid**. This is not a demonstrated raw sensor timestamp. In the 121.288-second candidate test it had four such gaps; `bleft` had one. Each was recorded as QC_ERROR under the existing threshold. Camera input/encoder/container counts agreed and the affected writer queues peaked at one frame; this does not identify the physical cause.
- The current media graph and camd mapping connect `right` to sensor `m01_b_sc233hgs`, media2 and `mipi2-csi2`, and `bleft` to `m03_b_sc233hgs`, media1 and `mipi1-csi2`. During the candidate test the five frame-grid gaps were close in time to CRC/frame-sequence events on their corresponding CSI paths. Similar mipi2 errors predate this update. Correlation and topology do not prove a cable, sensor, power, kernel or driver root cause.
- Read-only queries on camd's existing V4L2 descriptors returned NV12, 1920×1200, stride 1920, sizeimage 3456000 on all four output nodes. The reported crop is 1920×1080; compose was unavailable. The sensor subdevice pads report 1920×1080. The actual geometry transformation is not established; do not infer a driver clamp or modify capture parameters from those facts alone.

## Calibration and bounded tests

The selected `camera-camchain.yaml` declares 1920×1088 for all four topics; `camera_imu-camchain-imucam.yaml` and another historically archived, similarly named camchain file declare 1920×1200. Topic/role order is the same. The existing `camchain_camera_mapping_mismatch` reason compares both topic and resolution, so it does not by itself establish a role mismatch. The test snapshot correctly records these files as calibration candidates with applicability unverified. No intrinsic scaling, file replacement or recalibration was performed.

One controlled native boundary comparison was performed after stopping the controller and camd and confirming ownership release. It used the observed V4L2 multi-planar NV12 format/crop, six DMABUF buffers and `system-dma32`, without S_FMT, control writes or media-link changes. Rear-left alone, front-right alone and all four concurrently each reached the first-frame deadline without a frame; STREAMOFF/buffer release and process groups completed. Because camd/RKAIQ was stopped and all four channels failed in this changed ISP/3A condition, this is **not an equivalent-pipeline test** and cannot establish hardware failure. Original services were restored. No further resets or repeated sample selection were used.

After service restoration, one preselected 121.288-second candidate TEST with four headband cameras and board IMU completed START/black-screen ACK, refresh during the same recording, web long-press STOP, native/component shutdown receipt and save. The test recorded 3627–3638 camera frames and 24175 IMU rows, all checked arrival times within the start/stop gates, with no recording data file still open. The saved session is pending host QC and contains the five QC_ERROR frame-grid gaps above; it does not pass the quality gate. The full long videos were not separately decoded in this investigation. The two wrist nodes each returned ten 640×480 frames in an earlier idle check, but their left/right roles were unconfirmed and they were not part of this recording. EMG, EEG, physical phone touch, phone USB reconnect and physical wrist hotplug were not tested.

The software candidate has passed targeted local tests and 91 core tests on cp_0018's actual Python 3.8.10 in an isolated copy. An independent single-pair cp_0019 v8.1/candidate test exercised the same four headband cameras and IMU for approximately 11.5/11.9 seconds. Both saved pending QC; the baseline had two rear-right QC_ERROR gaps and the candidate had none. All eight short videos decoded, but one pair cannot establish long-term reliability or resolve cp_0018's failures. Daily-duration logic had 22 targeted tests pass; this is not a physical cross-midnight validation.
